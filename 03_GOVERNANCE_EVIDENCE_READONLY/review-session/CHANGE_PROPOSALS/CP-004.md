# Change Proposal: CP-004 — Deterministic Idempotency Key Architecture and Two-Phase Credit Reservation & Settlement Protocol

**CHANGE_ID:** CP-004  
**SOURCE_FINDINGS:** F-R02-003, F-R02-005, F-R07-004, F-R07-007, F-R14-001, F-R14-004, F-R14-005  
**TITLE:** Deterministic Idempotency Key Architecture and Two-Phase Credit Reservation & Settlement Protocol  
**STATUS:** PROPOSED (C03 Solution Design Complete)  

---

## 1. Problem Statement
Duplicate provider requests can trigger duplicate paid billing. Failed or crashed jobs can leak reserved credits without automatic reconciliation.

---

## 2. Current Specification Baseline (v0.9.0)
The v0.9.0 specification lacks formal schema definitions, explicit state boundaries, and robust error/concurrency semantics for this domain.

---

## 3. Proposed Specification Changes (Option A vs Option B)

### OPTION_A: Strongest Practical Solution (Recommended)
Database-backed two-phase credit ledger in R02 with transactional reservation and settlement.

**Exact Architectural Changes:**
Require idempotency_key = sha256(project_id + shot_id + prompt_version_id + seed + provider_params + attempt_index) on every provider request. Enforce Two-Phase Cost Protocol: 1. RESERVE_CREDITS(job_id, estimated_cost) -> 2. EXECUTE_PROVIDER_CALL -> 3. SETTLE_CREDITS(job_id, actual_cost, take_id) or RELEASE_CREDITS(job_id, reason). Add startup reconciliation daemon to auto-release stale reservations older than 90 minutes (1.5x max generation window of 60 minutes) or upon lease expiration.

### OPTION_B: Credible Alternative / Trade-off Analysis
Post-facto cost calculation from provider invoices without pre-allocation.
