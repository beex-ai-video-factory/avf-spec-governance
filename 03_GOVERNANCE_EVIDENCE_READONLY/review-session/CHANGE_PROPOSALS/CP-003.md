# Change Proposal: CP-003 — Optimistic Concurrency Control, Aggregate Version Fencing and Distributed Lease Protocol

**TITLE:** Optimistic Concurrency Control, Aggregate Version Fencing and Distributed Lease Protocol  
**STATUS:** PROPOSED (C03 Solution Design Complete)  

---

## 1. Problem Statement
Concurrent workflow workers or browser instances can race on updating ShotVersion, GenerationJob, or Take states, leading to lost updates and split-brain execution.

---

## 2. Current Specification Baseline (v0.9.0)
The v0.9.0 specification lacks formal schema definitions, explicit state boundaries, and robust error/concurrency semantics for this domain.

---

## 3. Proposed Specification Changes (Option A vs Option B)

### OPTION_A: Strongest Practical Solution (Recommended)
PostgreSQL optimistic locking with version column + Redis Redlock distributed worker lease management.

**Exact Architectural Changes:**
Mandate entity_version integer on all aggregate roots. All state mutations require expected_version fencing. Generation jobs acquire distributed leases with explicit TTL (default 120s) and periodic heartbeats. Stale worker writes with mismatched version or expired lease are rejected.

### OPTION_B: Credible Alternative / Trade-off Analysis
Pessimistic table locking on generation_jobs during the entire video generation.

---
